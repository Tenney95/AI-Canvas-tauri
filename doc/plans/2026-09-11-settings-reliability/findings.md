# 设置持久化核验依据

## 实施前仓库事实

- 当前配置通过 store.config.ts → storageService.ts → configPersistenceQueue.ts → indexedDb/catalogRepository.ts 保存。队列保存整份快照，不按字段合并。
- Key 与固定令牌通过 providerSecretService.ts → secret_store.rs 读写；普通配置记录只保存引用。
- secret_store.rs 使用进程内 Mutex 和临时文件 rename；Cargo.toml 已有 fs2，可评估复用跨进程文件锁，不新增依赖。
- configHydrated 已保护普通配置初始化失败时的默认值覆盖，但工具栏缺少相同保护。
- App.tsx 关闭路径只等待项目保存和部分清理，尚未等待配置保存队列。
- 根目录现有 task_plan.md / findings.md / progress.md 属于其他工作，本任务使用独立专项目录。

## 故障验证

上一轮以实际源模块加内存存储替身复现 4 个场景：MCP 读取失败覆盖原令牌；主题内存已修改但磁盘未保存且 Promise 未拒绝；工具栏失败加载后覆盖旧布局；旧实例全量保存覆盖新主题。仅使用隔离数据，未操作用户真实凭据或运行中应用。

上一轮既有回归 5 文件、84 项通过；这是已有覆盖的基线，不代表新增可靠性目标已实现。

## 外部资料

- IndexedDB 标准定义事务持久性提示；strict 旨在优先同步持久化，仍不是免除所有故障的承诺：https://www.w3.org/TR/IndexedDB/
- Chromium 文档说明 readwrite 的 relaxed 与 strict 在 complete 时机的差异：https://developer.chrome.com/blog/indexeddb-durability-mode-now-defaults-to-relaxed
- Tauri Store 官方文档说明它是可异步保存/加载的文件键值存储；自动保存存在防抖延迟，仍需要应用处理调用时序：https://v2.tauri.app/plugin/store/
- Tauri SQL 插件支持 SQLite，接入需要插件依赖与迁移定义；不是当前已经安装的配置后端：https://v2.tauri.app/plugin/sql/
- Stronghold 需要密码派生配置并从带密码的快照加载，属于加密凭据方案；不能据此断言其不会读取失败：https://v2.tauri.app/plugin/stronghold/
- Chromium 文档明确 strict 只改变关键持久性完成时机，不能保证没有数据丢失；本方案只考虑低频配置写入，不改变全部数据库写入策略。
- fs2 官方说明文件锁的跨平台边界；本次使用独立文件句柄与有界 try_lock_exclusive，不混用同一文件的克隆句柄：https://docs.rs/fs2/latest/fs2/trait.FileExt.html
- IndexedDB transaction 的官方参数说明包含 strict durability 及异常分类：https://developer.mozilla.org/en-US/docs/Web/API/IDBDatabase/transaction

## 实施选择

- 根据当前缺陷和迁移成本，推荐保留现有介质并修保存协议。SQLite/Stronghold 本轮不安装，不迁移用户数据。
- 已核验 useToolbarEdit.exitEdit 先退出再提交，需与 Store 的失败状态一起修改，才能保留可重试草稿。
- 已有 ui-badge/ui-alert 等组件样式可复用，不新增全局颜色或样式体系。
- 普通设置目前每次保存都会核对全部凭据，这是无关设置被凭据故障牵连的直接原因；保存意图分离比永久缓存明文更合适。
- 跨实例保护仅针对遵守新协议、访问同一存储源的客户端；旧版本或不同来源不能作无限保证。
- 新增原生锁文件必须仍在私有目录，且所有拒绝路径覆盖它。备份恢复不能复活用户已撤销的令牌。

## 第一阶段结果与限制

- MCP 原先吞掉读取错误并覆盖令牌的入口已消除；初始化合并并发调用，设置页读取运行中令牌不触发创建，轮换失败保留实际活动令牌。
- 工具栏的读取失败不再返回空值；Store 在成功加载前拒绝保存，读写等待事务完成/中止。按类型局部事务保留其他实例的不同类型修改；同类型冲突仍需后续处理。
- 工具栏保存成功才提交内存并关闭编辑，失败及保存期间的新修改保留草稿；长按不会再次切换掉尚未保存的编辑。
- 分类只识别可信白名单代码/标准错误名。当前 Rust 字符串无法可靠区分权限、锁占用与磁盘故障，因此按 unknown 失败关闭，不从错误正文猜测重试。
- 真实文件访问失败的具体现场原因仍未证实；本次仅使用隔离数据故障注入，没有读取用户凭据或启动/关闭其应用。

## 第二阶段结果与限制

- 普通配置使用三方比较及单个 IndexedDB 事务，独立字段合并、同字段冲突拒绝。API Key 和旧模型 Key 不进入保存基线；主题等无关更新不再核对全部凭据。
- 原 Store 默认把保存失败作为成功 Promise 返回，导致调用方继续提示成功；现改为全部拒绝，UI 保留输入并提供重试。保存完成时用修改序号和快照差异保留后续编辑。
- 独立素材窗口原先读取整份配置并直接回存，圆环菜单原先失败后仍关闭；两个追加入口均已确认并完成定向交互回归。
- 退出不仅要等待共享保存队列，还需收集尚未进入队列的尺寸防抖及工具栏本地草稿。先收集再冻结，失败保留取消退出和显式重试；不因排空完成就假定保存成功。
- 旧模型迁移必须位于凭据迁移之前，否则新的普通字段补丁可能漏掉旧模型携带的 Key 或归一化字段。已用真实 Store → 存储服务 → 隔离 IndexedDB 验证迁移、失败保留和后续零凭据 IPC 保存。
- 配置 Key 版本会阻止遵守协议的旧客户端提交陈旧凭据，并阻止把已变化版本的缓存 Key 当成当前值；该前端版本不等于 Rust 条件更新。原生锁、条件提交、凭据删除时序及同类型布局冲突仍需第三阶段。

## 第三阶段结果与限制

- 原生锁覆盖凭据文件读取、条件比较、写入与删除，获取超时返回 busy；阻塞操作在线程池执行。所有调用使用同一私有锁文件，旧版未参与此协议的进程不具备同等竞争保护。
- 临时文件完成写入并 sync_all 后替换主文件，再同步主文件；Unix 额外同步父目录。暂存失败与解析损坏不会覆盖原记录。现有 Windows 文件替换和文件系统仍可能失败，不能据此保证断电零丢失或 Windows 目录元数据的绝对持久性。
- 普通配置与原生凭据仍是两个介质。删除动作将渠道移除与 _pendingSecretCleanup 指纹放在同一数据库事务，提交成功后才条件删除；失败可恢复，值已变化则取消旧清理。已提交状态推进基线，不把清理失败伪装成整次未提交。
- 配置和布局事务请求 strict durability；仅明确不支持参数的错误兼容回退，不把权限或容量错误当成兼容问题。未新增 object store 或 schema 版本。
- 工具栏同类型提交在数据库事务内比较编辑基线，冲突后保留基线和草稿；用户确认重新加载才放弃草稿。不同类型仍局部合并。
- 隔离数据验证已覆盖真实子进程竞争、条件更新/删除、异常退出释放锁、配置提交中止与清理部分成功。具体现场读取失败的系统原因仍未证实，真实桌面退出重开、Unix 和断电验收未进行；默认特性 Rust 测试还受现有 ONNX/MSVC 链接兼容问题限制。
