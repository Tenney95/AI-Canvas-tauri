# 打包与发版流程

> 适用于已启用 `createUpdaterArtifacts`、自动更新和 GitHub Actions 质量门禁的版本。
> 当前版本以 `package.json` 为唯一来源，不在本文档中固定具体版本号。

## 前置准备

### 需要的文件 / 配置

| 文件 | 作用 |
|---|---|
| `package.json` → `version` | 前端版本号（唯一来源） |
| `src-tauri/tauri.conf.json` → `version` | Tauri 版本号，运行时读取 |
| `src-tauri/Cargo.toml` → `package.version` | Rust 编译版本号 |
| `src-tauri/update-key.key` | 签名私钥（**敏感，勿提交**） |
| `src-tauri/update-key.key.pub` | 签名公钥（已写入 `tauri.conf.json` 的 `plugins.updater.pubkey`） |
| `src-tauri/tauri.conf.json` → `bundle.createUpdaterArtifacts` | 设为 `true`，构建时生成 `.sig` 签名文件 |
| `.github/workflows/ci.yml` | PR 与 `master` push 的前端质量检查和 Rust 检查 |
| `.release-notes.md` | 当前版本的 Release notes 审阅稿；每次发版覆盖，历史版本由 Git 记录保留 |
| `.github/release-title.txt` | 一行完整 Release 名称，版本须与目标标签和 `package.json` 一致 |
| `.github/workflows/release.yml` | Tag 转交默认分支发布、同 SHA 门禁与产物核验；Windows、macOS 两个标准平台与 Windows Legacy 并行，全部成功后公开 |

### GitHub Secrets（无需每次修改）

在仓库 **Settings → Secrets and variables → Actions** 中配置：

| Secret | 值 |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | `update-key.key` 文件内容（一行 `dW50cnVzdGVk...`） |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 生成密钥时设置的密码 |

> 密钥通过 `npx tauri signer generate -w ./src-tauri/update-key.key -f -p "<签名密码>" --ci` 生成。
> 每次重新生成密钥后，必须连同 `tauri.conf.json` 中的 `pubkey` 一起更新。
> 私钥、签名密码和包含它们的终端输出不得提交到仓库或写入发版记录。

### macOS 临时签名与首次打开

后续版本的 macOS 安装包仅发布 M 系列芯片（Apple Silicon）的 `aarch64-apple-darwin` 目标，不再构建或发布 `x86_64-apple-darwin`；已发布的历史安装包保留。

当前 GitHub 发布工作流为 Apple Silicon 安装包设置 `APPLE_SIGNING_IDENTITY=-`，由 Tauri 在打包前完成应用和所包含代码的临时签名（ad-hoc）。无需配置六个 `APPLE_*` Secret，也不执行 Apple 公证和票据装订。上表中的 Tauri 更新器密钥仍用于生成 `.sig`，与 macOS 代码签名分别管理。临时签名配置见 [Tauri 的 macOS 签名说明](https://v2.tauri.app/distribute/sign/macos/#ad-hoc-signing)。

macOS 任务验证签名完整性和 `Signature=adhoc`，随后在 GitHub macOS runner 上尝试启动应用。所有平台任务成功后才将 Release 草稿公开。该检查只验证 runner 上的签名和启动，不能代表浏览器下载后通过 Gatekeeper；发布后仍需在另一台 Mac 上下载 `.dmg`，核对安装和首次打开。

浏览器下载可能添加 `com.apple.quarantine` 隔离属性，构建时清除该属性无法阻止下载时重新添加。临时签名包没有 Apple 公证，安装到「应用程序」后首次打开可能被拦截，可在「系统设置 → 隐私与安全性」中选择「仍要打开」。若提示应用已损坏，确认下载的是本仓库发布包后，可在本机终端运行：

```bash
xattr -dr com.apple.quarantine "/Applications/AI Canvas.app" && open "/Applications/AI Canvas.app"
```

该命令仅清除指定应用的下载隔离属性并打开应用，不重新签名；安装路径不同则替换应用路径。首次打开方式见 [Apple 的说明](https://support.apple.com/zh-cn/102445)。如以后恢复 Developer ID 签名和 Apple 公证，需要重新接入证书、公证凭据及相应 CI 校验。

## 第一步：版本号同步

### 1.1 修改 `package.json` 的 `version`

例如将当前版本 `X.Y.Z` 更新为目标版本，并确保符合语义化版本规则。

### 1.2 运行同步脚本

```powershell
npm run sync-version
```

这会自动同步版本号到：
- `src-tauri/Cargo.toml`（Rust 编译时不再显示旧版本）
- `README.md`（版本 badge）

同步脚本当前不会更新其他语言 README、站点或说明书。还需核对：

- `README.en.md`、`README.ja.md`、`README.ko.md` 的版本徽章与核心能力；
- `site/index.html` 的版本及下载文案；
- `site/manual.html` 的标题、版本、核对日期、正文操作入口和截图说明；
- `site/README.md` 的维护流程，以及受影响的当前模块文档；
- `package-lock.json` 的根版本与 `packages[""].version`，以及 `src-tauri/Cargo.lock` 的应用包版本（不改依赖解析结果）。

说明书可以记录后续源码功能，但必须明确区别于当前发布包，不能仅把版本号替换后宣称新功能已发布。纯文档更新检查链接、UTF-8、脚本和图片完整性；实际发布仍执行后面的质量门禁。

四份 README 的版本徽章应同步核对，能力正文只在对应修改获得授权时调整。更新当前架构文档时，从 `useAppStore.ts` 核对 slice 清单、从 `indexedDb/schema.ts` 读取 `DB_VERSION`；历史测试结论不改写为本次通过。最新准备见[v0.11.4「角色形象工作台与模型互通」](./plans/2026-11-13-release-0.11.4.md)，以已公开 v0.11.3 为基准。源码 CI 与标准／Legacy 构建固定 Rust 1.99.1，当前 ONNX 依赖尚未适配 Cargo 1.100 的中间目录变化，升级工具链前须核对 DLL 复制与打包。实际门禁与发布证据留在 Actions Summary，不为补成功流水重新触发门禁。历史见[发布记录](./发布记录.md)，文档维护从[导航](./文档导航.md)与[专项索引](./plans/计划索引.md)进入。

### 1.3 手动修改 `src-tauri/tauri.conf.json`

```json
"version": "X.Y.Z"
```

> 三处版本号（`package.json`、`tauri.conf.json`、`Cargo.toml`）必须一致。

## 第二步：编写 Release notes（发布说明）

Release notes（发布说明）面向安装或升级应用的人，说明本次更新的用户价值、兼容性影响和安装包选择。正文只维护 `.release-notes.md`，标题只维护 `.github/release-title.txt`，工作流从目标标签源码读取，不在 YAML 中重复抄写。

### 2.1 确认事实来源

以最近一个正式 Tag 为比较基准，检查该 Tag 到当前 `HEAD` 的提交和文件差异：

```powershell
$previousTag = "vX.Y.Z"
git log --oneline "$previousTag..HEAD"
git diff --stat "$previousTag..HEAD"
git diff --name-status "$previousTag..HEAD"
```

编写时遵守以下规则：

- 每项更新必须能追溯到提交、代码差异或已通过的测试
- 不根据计划文档、未合并分支或未完成代码推测发布内容
- 不直接复制提交列表，应合并重复提交并转换为用户可理解的结果
- 纯文档、测试和内部重构通常不进入正文，除非它们改变用户行为或兼容性
- 上一版本仍然存在的平台限制必须继续说明，不能因本次未修改相关代码而省略

### 2.2 组织标题和正文

Release 名称使用 `AI Canvas vX.Y.Z - 版本主题`。版本主题应概括最重要的用户变化，避免使用“体验优化”“问题修复”等无法区分版本的泛化表述。

正文按以下顺序组织：

1. **版本摘要**：用 1 至 2 句话说明核心价值，不重复罗列所有条目
2. **主题分组**：按角色库、画布、对话助手、媒体生成等用户任务分组，通常保留 2 至 4 组
3. **升级与兼容性**：存在数据迁移、行为变化、功能缺失或平台限制时必须添加
4. **下载说明**：列出当前实际生成的 Windows、macOS 安装包（Linux 暂停构建，用户明确要求后再恢复）

每个条目只表达一个可验证的变化。优先使用“新增”“支持”“优化”“修复”“调整”等明确动作，并写出变化对象和结果。不要使用“若干优化”“提升稳定性”“改善体验”等缺少事实范围的描述。

以下内容必须在适用时写入：

- 破坏性变更、配置重置、数据迁移和不可逆操作
- 厂商、模型、计费方式或所需 API Key 的变化
- 操作系统、CPU 架构和本地运行时限制
- 已知问题及可执行的规避方式

不得写入 API Key、签名私钥、完整本地路径、内部调试日志或未公开的服务地址。

### 2.3 使用固定模板

更新根目录下固定的 `.release-notes.md`，每次发版直接覆盖上一版正文，历史内容由 Git 记录保留。正文使用以下模板。没有兼容性内容时，删除整个“升级与兼容性”小节，不保留空标题。

```markdown
## ✨ 版本摘要

release_summary_here

## feature_theme_here

- user_visible_change_here

## ⚠️ 升级与兼容性

- compatibility_or_limitation_here

## 📦 下载

- 🪟 Windows：使用 `.exe` 或 `.msi`。
- 🍎 macOS：仅提供 M 系列芯片（Apple Silicon）的 `aarch64.dmg`，不再发布 Intel 安装包。
- Linux：暂停构建安装包，历史版本保留，恢复须由用户明确提出。
```

主题标题可以使用一个与内容匹配的图标。正文条目不添加装饰图标，避免影响扫描。

### 2.4 核对标题与目标源码

审阅 `.release-notes.md` 后，核对 `.github/release-title.txt` 与目标源码：

- 标题完整使用 `AI Canvas vX.Y.Z - 版本主题`，只有一行，主题与正文一致
- 正文与版本资料使用同一个 `X.Y.Z`，不需要改写工作流正文
- 标题、正文、五份版本文件与标签一起进入同一提交；默认分支编排不能误用其最新版本文案替代目标标签的文案
- 下载说明与构建矩阵实际生成的产物一致

在 Tag 推送前完成文案同步。Tag 推送后不得改写同名 Release 来掩盖代码与文案不一致；应修复代码或文案后发布新的补丁版本。

### 2.5 Release notes 检查清单

创建发版提交前逐项确认：

- [ ] 比较范围从上一正式 Tag 到当前 `HEAD`
- [ ] 每条内容都能追溯到代码差异或测试结果
- [ ] 标题和摘要说明本次版本的主要用户价值
- [ ] 内部实现细节已转换为用户可理解的行为变化
- [ ] 数据迁移、平台限制和已知问题没有遗漏
- [ ] 工作流从目标标签读取 `.release-notes.md`，不另维护一份 YAML 正文
- [ ] Release 名称、正文和版本文件使用同一个版本号
- [ ] 下载说明与当前构建矩阵一致
- [ ] 文案不包含密钥、完整本地路径或内部日志
- [ ] 文件通过严格 UTF-8 解码和乱码扫描

## 第三步：质量门禁

本地完整门禁在原子推送前完成。同一提交的远端前端与 Rust CI 必须在安装包构建前成功；标签可以与 `master` 同批推送，但此时只是发布请求，不代表已经获得打包或公开许可。失败或缺少可信证明时停止发布。

### 3.1 前端检查

```powershell
npm run ci
```

`npm run ci` 当前依次执行：

- 全仓 ESLint（零告警）；
- 前端生产代码类型检查；
- 测试代码类型检查；
- Vitest 自动化测试。
- 前端生产构建。

正常发版由 `pre-push` 自动执行这套命令，不在推送前手动再跑一次。需要重装依赖时单独运行 `npm ci`；不增加按 HEAD 或时间戳猜测成功的本地缓存，也不为本次发版删测试、扩大超时或直接开启全量并行。

> lint 已恢复为本地与 CI 的必过门禁。`eslint.config.js` 排除 Rust 构建产物、原生生成目录、vendor 和独立宣传视频项目；若检查失败，定位实际路径并修复，不跳过门禁或降级依赖来掩盖错误。

### 3.2 Rust 检查

自动发布以同 SHA 源码 CI 的 `Rust check` 汇总结果为准。该任务等待 Windows、macOS 和 Linux 检查通过。以下命令只在已获授权的本地排查或构建验证中使用：

```powershell
Set-Location src-tauri
cargo check --lib --locked
cargo test --lib --locked native_project_media::tests::windows_media_
Set-Location ..
```

### 3.3 CI 检查

推送到 `master` 或创建 Pull Request 后，`.github/workflows/ci.yml` 自动执行：

1. Ubuntu 前端 job：`npm ci` → `npm run ci`；
2. Windows、macOS、Linux 并行运行 `cargo check --lib --locked`。Windows 另外验证原生素材发布与中断恢复。
3. `Rust check` 汇总任务要求平台矩阵全部成功，继续作为 Release gate 核验的固定任务名。

`Frontend quality` 和 `Rust check` 汇总任务通过后，目标提交才具备安装包构建条件。Release gate 等待并核验同仓库默认分支 push、精确 SHA 的成功 CI，同时核验前端产物来源。缺失、失败、取消或超时均阻止打包。可信产物缺失或过期时先重跑对应源码 CI。

## 第四步：本地构建（可选）

自动发布通常跳过本节与手动 `latest.json` 步骤，统一由 Actions 打包和签名。仅在明确需要本地安装包或本地排查时执行，不与远端打包机械重复。

### 4.1 设置环境变量

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY = (Get-Content "src-tauri/update-key.key" -Raw).Trim()
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = "<签名密码>"
```

> `Get-Content -Raw` 读取文件内容，`.Trim()` 去除尾随换行符，防止 base64 污染。
> `<签名密码>` 替换为生成密钥时设置的密码，不要把真实密码写入脚本或文档。

### 4.2 构建

```powershell
npm run tauri build
```

构建完成后产物位置：

```
src-tauri/target/release/bundle/
├── nsis/
│   ├── AI Canvas_X.Y.Z_x64-setup.exe      ← 安装包
│   └── AI Canvas_X.Y.Z_x64-setup.exe.sig  ← 签名文件
├── msi/
│   ├── AI Canvas_X.Y.Z_x64_en-US.msi
│   └── AI Canvas_X.Y.Z_x64_en-US.msi.sig
└── ...
```

### 4.3 检查产物

确认以下文件均已生成：
- `.exe` / `.msi` 安装包
- 对应的 `.sig` 签名文件
- 终端无报错

## 第五步：创建 `latest.json`

Tauri 更新器通过拉取 `latest.json` 来判断是否有新版本。本地构建不会自动生成此文件。

### 5.1 模板

```json
{
  "version": "X.Y.Z",
  "notes": "本版更新说明……",
  "pub_date": "2026-07-06T11:30:00Z",
  "platforms": {
    "windows-x86_64": {
      "signature": "<把 .sig 文件内容贴到这里>",
      "url": "https://github.com/Tenney95/AI-Canvas-tauri/releases/download/vX.Y.Z/AI.Canvas_X.Y.Z_x64-setup.exe"
    }
  }
}
```

- `signature`：复制 `AI Canvas_X.Y.Z_x64-setup.exe.sig` 文件里的全部内容
- `url`：GitHub Release 的直接下载链接。注意 GitHub 会把文件名中的空格替换为 `.`
- `pub_date`：当前 UTC 时间，格式 `YYYY-MM-DDTHH:mm:ssZ`

### 5.2 上传方式

**通过 CI 自动发布（推荐）**：跳过此步，`tauri-action` 的 `includeUpdaterJson: true` 会自动生成并上传。

**手动发布**：需自行创建 `latest.json` 并上传到 Release Assets。

## 第六步：发布 GitHub Release

### 方式 A：自动发布（推荐）

```powershell
git status --short
git add <本次发版文件>
git commit -m "chore(release): 发布 vX.Y.Z"
# 在 master 上，确认版本资料与标签指向同一提交
git tag -a vX.Y.Z HEAD -m "vX.Y.Z 版本主题"
git push --atomic origin master refs/tags/vX.Y.Z
```

版本号、说明、模块资料先一次准备并提交，代码和标签一次原子推送，避免分开推送重复执行本地完整门禁。不要仅为补写一条成功流水再提交、推送一次；源码 SHA、CI 与产物来源由 Actions Summary 留证，必要的后续文档修订合并到下一批授权推送。

推送 tag 后，`.github/workflows/release.yml` 自动触发：

1. 标签运行只转交发布请求；实际发布从仓库默认分支启动，始终检出目标标签的固定 SHA。手动启动也须在默认分支，并明确填写目标标签；不修改正在执行的旧版工作流。
2. `quality` 等待目标 SHA 的默认分支 push CI，核验前端与 Rust 均成功、产物完整且来源对应；不重复运行这份已证明成功的完整检查，失败或超时停止。
3. 下载并校验这份 CI 前端产物，使用固定发布配置复用前端并准备 MCP 适配器；普通本地构建保持原流程。
4. Windows、macOS 两个标准平台和 Windows Legacy 同时构建，各自使用隔离的 npm／Rust 缓存；Legacy 不等待标准包完成再开始。macOS 临时签名和启动检查保留。
5. 标准包生成 `.sig`、`latest.json` 与 Release 草稿；Legacy 先保存到 Actions 产物。最后任务等待所有平台验证成功，再上传 Legacy 并公开 Release。

实际发布放在默认分支是为了让不同版本复用原生缓存：GitHub 限制不同标签之间直接互读缓存。构建仍固定到目标标签，不以默认分支最新源码代替；首次冷缓存和工具链变化仍可能较慢。详见[发布加速专项](./plans/2026-11-07-release-acceleration.md)与[GitHub 缓存限制](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache)。

#### 自动发布的交付节点：平台构建启动后无需继续等待

当同一发布提交满足以下条件时，助手即可结束本轮等待并向用户交付版本号、Tag 和 Actions 工作流链接：

- `CI / Frontend quality` 与 `CI / Rust check` 已成功；
- 默认分支实际发布运行的 `Release / Quality gate` 已成功，并在 Summary 标明目标标签和源码 CI；
- 两个 `Release / Publish` 平台任务（Windows、macOS Apple Silicon）均已启动，显示 `In progress`，且没有失败或取消。

此时 GitHub 总状态仍可能显示 `Some checks haven't completed yet`，属于安装包构建中的正常状态。无需持续轮询，也无需等待全部安装包、Windows Legacy、签名上传和最终公开完成；后续由 Actions 按既有依赖顺序自动执行。不额外创建定时监控，除非用户明确要求继续跟进。

交付时应明确写“发布构建已启动，后台自动完成”，不能写“安装包已发布完成”。最终公开仍以工作流全部成功和 Release 状态为准；用户明确要求验收安装包或跟踪至公开时，再继续检查对应产物与结果。

> 发布 Tag 应视为不可变。Tag 推送后发现问题时，修复代码并发布新补丁版本，禁止覆盖已经发布的 Tag。

### 方式 B：手动发布

1. 打开 https://github.com/Tenney95/AI-Canvas-tauri/releases/new
2. Tag 填 `vX.Y.Z`，Release title 填 `AI Canvas vX.Y.Z`
3. 上传以下文件到 Assets：
   - `AI Canvas_X.Y.Z_x64-setup.exe`（安装包）
   - `AI Canvas_X.Y.Z_x64-setup.exe.sig`（签名）
   - `latest.json`（版本描述）
4. 使用 `.release-notes.md` 的正文填写 Release notes，点击 **Publish release**

> 手动发布时必须上传 `latest.json`，否则自动更新会报 `Could not fetch a valid release JSON`。

## 第七步：验证更新

### 7.1 本地验证

1. 安装目标版本的上一版本
2. 重新构建安装包并安装
3. 启动应用 → 观察控制台 → 应自动拉取 `latest.json` 并开始下载新版本
4. 下载完成后应用自动重启至新版本

### 7.2 验证要点

- 控制台输出 `[Updater] 发现新版本 vX.Y.Z，开始下载...`
- 进度条显示下载进度
- 下载完成后自动安装并重启
- 重启后版本号显示为新版本
- 如果在已是最新版的机器上打开，输出 `当前已是最新版本`
- GitHub Release 的名称和正文与审阅稿一致
- GitHub Release 不是草稿或预发布版本
- Release Assets 包含目标平台安装包、签名文件和 `latest.json`

### 7.3 常见问题

| 现象 | 原因 | 解决 |
|---|---|---|
| `开发模式，跳过更新检查` | `npm run tauri dev` 运行 | 正常，打包后自动不跳过 |
| `Could not fetch a valid release JSON` | `latest.json` 未上传到 Release Assets | 手动上传 |
| `pubkey is not valid` / 签名验证失败 | 本地构建用的 key 与 GitHub Release 的签名不匹配 | 确保用同一密钥对 |
| `failed to decode secret key` | 环境变量未设置或 base64 含换行符 | `Get-Content -Raw` 后加 `.Trim()`，并设置密码 |
| `failed to decode base64 secret key` | `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 未设置 | 检查密码是否与生成密钥时一致 |
| Release 的 `publish` 未启动 | 同 SHA 源码 CI 未成功，或可信前端产物缺失 | 查看 Quality gate 的 Summary 与对应源码 CI；等待或重跑原 CI，修复源码则使用新补丁标签 |
| 默认分支实际发布未启动 | 标签运行未完成转交，或手动运行分支／标签错误 | 查看标签 dispatcher；仅对未公开标签，从默认分支手动启动并明确填写目标 tag |
| CI 中 lint 未执行 | 工作流或 `package.json` 未使用当前门禁 | 核对 `npm run ci` → `check` → `lint` 调用链，恢复完整检查后再发布 |

## 一图流

```
修改 package.json version
        │
        ▼
npm run sync-version  ──→ 同步 Cargo.toml + README
        │
        ▼
手动改 tauri.conf.json version
        │
        ▼
更新 .github/release-title.txt + .release-notes.md
一次完成版本、说明书与模块资料并提交
        │
        ▼
标签与 master 指向同一提交
git push --atomic origin master refs/tags/vX.Y.Z
（pre-push 完整执行一遍 npm run ci）
        │
        ▼
标签 dispatcher → 默认分支发布编排
等待同 SHA 的源码前端与 Rust CI 成功
        │
        ▼
复用并校验同 SHA 的 CI 前端产物
Windows / macOS / Legacy 并行构建（Linux 安装包暂停）
（固定目标源码 + 隔离缓存）
        │
        ▼
全部平台验证通过 → 上传 Legacy → 公开 Release
签名和 latest.json 由工作流生成
        │
验证结果与产物来源写入 Actions Summary
不为逐次补成功流水再次提交、推送
```

本地安装包与手动上传是可选排查／分发路径，见第四、第五步和方式 B，不插入上述自动发布关键路径。已包含本批加速脚本、配置和标题元数据的未公开标签需要重新启动时，可在默认分支运行 `gh workflow run release.yml --ref master -f tag=vX.Y.Z`；已公开版本不可借此改写。旧标签没有这些文件时不能用新编排强行补跑；新流程从包含本批改动的下一版本生效，已运行的旧版工作流继续原流程。
