# Task Plan: 全局智能体兼容体系方案

## Goal

## Key Questions

1. 如何让智能体全局可用，同时允许项目级启用、禁用和覆盖，而不复制整套配置？
2. 如何把一个复合智能体拆成可按需加载的路由、Skill、知识源、工具、模型策略、资产源和子智能体？
3. 如何复用当前 Agent Runtime 和 Tool Registry，而不是新建第二套执行引擎？
4. 如何在不泄露绝对路径、不自动执行不可信脚本的前提下支持外部知识库？
5. 如何让同一智能体同时服务普通聊天、画布项目、独立窗口、后台任务和 MCP？

## Decisions Made

| Decision | Rationale |
|----------|-----------|
| 阶段 1-5 只做架构方案，不实施 | 架构收敛先经过用户审核，避免未经确认的大范围修改 |
| 智能体定位为全局能力包，不等同于项目或单个 Skill | 用户明确要求全局可调用，短剧样板也包含多 Skill、知识、资产和门禁 |
| 优先复用现有 Agent Runtime 与 Tool Registry | 避免形成两套权限、任务、审批和审计体系 |
| 单任务只允许一个主编排智能体 | 防止多个总控智能体产生冲突目标、重复工具调用和相互覆盖 |
| 其他智能体作为专家或能力提供者 | 保留多智能体分工，同时让主任务拥有唯一决策与落地责任 |
| 不使用隐藏“全局项目”模拟全局任务 | 避免删除、项目切换、记忆和任务索引继续继承错误语义 |
| 软件只内置通用平台，不内置 AI 短剧智能体 | 用户要求所有业务智能体都由用户主动上传，避免产品与某个业务知识库耦合 |
| 项目只保存全局安装 ID 和覆盖项，不保存包内容 | 防止项目体积膨胀、版本分叉和知识库被复制污染 |
| 无智能体时完全旁路兼容层 | 用户要求没有智能体也不影响其他功能；原生聊天、画布、工作流和模型链必须保持当前行为 |
| 智能体故障采用 fail-open 到原生能力，涉及其专属任务采用 fail-closed | 普通功能不中断，但不能在包缺失或内容漂移时假装智能体任务成功 |
| 首版使用独立 Agent Catalog DB，不升级核心业务 DB | 把可选子系统的迁移、损坏和多窗口阻塞风险与项目、聊天等核心数据隔离 |
| 固定包清单名为 `ai-canvas-agent.json`，旧目录使用宿主侧适配清单 | 建立可验证的通用合同，同时不要求修改用户现有知识库 |
| 用户已授权按方案开始实施 | 2026-08-27 用户明确要求迁移文档并开始实施，且上传入口放入内部助手 |
| 上传首批支持文件夹与压缩包两种选择 | 文件夹用于 linked 大型知识库，压缩包用于 managed 安装 |
| 现有 `Cargo.toml` 与生成 schema 改动视为用户改动 | 实施时避开覆盖，新增依赖仍需单独确认 |
| 首批压缩包采用 tar.gz 内核 | 复用现有 Rust 依赖完成安全实现；普通 `.zip` 需要新增直接依赖，暂不越过确认点 |

| `git fetch myfork master` 连接失效代理 `127.0.0.1:7892` 失败 | 1 | 本次 fetch 显式清空 HTTP/HTTPS proxy 后直连成功，未修改永久代理配置 |
